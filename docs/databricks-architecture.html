Policy Red Team on Databricks

A Node and TypeScript service that reads a policy paper the way an adversary would. On Databricks it runs as one App, keeps its assessments in Lakebase Postgres, and calls a Model Serving endpoint as its own service principal. No API keys are stored anywhere.

In plain English

What it does

You give it a policy paper. It reads the paper the way someone looking for a way round it would, and tells you where the policy is exposed.

For each organisation the paper involves, it asks three questions. What does this body want? What does the policy make it pay for, or blame it for? And what could it do to serve itself at the policy's expense, while staying within the rules? The plays that stay within the rules matter most, because nothing in the policy will stop them.

  1. 1

    Upload a paper

    A PDF, Word document or text file, with a title. Choose how many model calls run at once.

  2. 2

    It works through 18 stages

    Reads the paper, works out who is in it, tests it, attacks it, then writes it up and challenges its own conclusions. About an hour for a short paper.

  3. 3

    Read the report

    In the browser, or downloaded as Word, markdown, or a pack that opens offline.

An example, from a real run

The sample paper is six sentences about a local access programme: the Department commissions the Council, the Council is accountable and bears the cost, and Providers supply data to the Council, but no data-sharing payment or enforcement power is specified. From that, the run found 17 plays across the three bodies. Four of them:

The model scores each play on four factors, from 0 to 1. The app ranks them by exposure, the geometric mean of the four, so a play that is weak on any one factor ranks low. The coordinated slow-down would hurt, but it is hard to organise and easy to spot. The three above it are easy, deniable and entirely allowed, which is what makes them the real risk.

What it is not

  • Not an assurance review. It never says a policy is fine. A clean report means it found nothing, which is not the same thing.
  • Not about people. Every profile is a hypothesis about an organisation's incentives, never a finding about a named person.
  • Not the last word. Findings rest on the paper alone while web research is off, and the report says so.
  • Not a government service. It uses the GOV.UK Design System for its forms and documents, without the crown, the royal arms or the GDS typeface.
The system

What runs where

Everything a reader touches is one process inside one App. The platform puts the workspace sign-in in front of it and hands it credentials at start-up. The process keeps no state on its own disk, because the App's filesystem is wiped on every restart.

A run

From upload to report

An assessment is a queue of eighteen stages kept in Lakebase. Two worker loops (POLICY_WORKERS) each claim one stage at a time, so two documents can be in progress together. Within a stage, calls run four at a time by default, chosen on the submit form. Because every step is a row in Postgres, a restart loses at most the call in flight, and the stopping instance hands its claims straight back to the queue.

Deployment

How it gets there

The App is built on the deployer's machine and uploaded ready to run. Deploying the repository and letting the platform run npm install failed three times: Databricks' registry mirror refused a different package on each attempt, while serving the same files to a laptop. The staged build removes that step entirely.

First deployment

  1. npm ci
  2. databricks bundle run init_secrets -t dev
  3. databricks bundle deploy -t dev
  4. databricks bundle run policy_red_team -t dev
  5. Set a token ceiling in /admin, then grant CAN_USE

Another workspace

Add a target to databricks.yml with that workspace's host and, if needed, a different serving_endpoint. Nothing else in the repository names a workspace.

Limits and open items

What to know before relying on it

Cost

A full run on a one-page sample used 5.6 million tokens, 4.97 million of them input, in about 1 h 45 m. Every call resends the shared context: Claude on Serving accepts cache markers, but a probe read the cache only once in four calls, so caching is an experiment behind POLICY_DATABRICKS_PROMPT_CACHE. Set a token ceiling in /admin and rate limits on the endpoint's AI Gateway before sharing.

Restarts

The platform gives a stopping App 15 seconds, and a stage can take minutes. After 10 seconds the App hands its claimed stages back to the queue, so the next instance picks them up within a second. The call in flight is lost and still billed; the stage resumes.

Sealed runs

Their keys are files on local disk, so an App restart destroys them. Leave sealing off until the keys move to somewhere durable, such as a Unity Catalog volume.

Output limits

Claude writes its reasoning inside the reply, so it spends the same output budget. The first two runs each lost their final stage at exactly the pipeline's 25,000-token cap. Claude now gets 48,000 tokens, and a request that was cut off once gets 64,000 on its next attempt, sized on the measured rate of about 110 tokens a second.
